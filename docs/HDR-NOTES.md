# HDR 映射：算法、参数与实测验证

本文是本项目 HDR 部分的**唯一权威说明**：算法每一步做什么、参数怎么影响画面、
以及 2026-10-11 做的那次对照复现发现了什么。

---

## 1. 设计原则：把「哪里亮」和「多亮」分开

单图转 HDR 有两种做法：

1. **端到端生成**：让扩散模型直接吐出 HDR 图。问题：模型会**重画**细节——
   人物轮廓、线稿边缘、服饰花纹都会被"想象"一遍，4K 原图的锐度反而丢了。
2. **语义定位 + 物理映射**（本项目的做法）：模型只回答**哪里应该更亮**（低分辨率、场景线性的高光场），
   **多少 nit 由显式单调曲线决定**，色度和几何完全沿用原图。

第 2 条带来了三个实际好处：

* **可调**：改 `peak_nits` / `knee` 不需要重跑模型（缓存 `.npy`）；
* **可信**：图像内容不被模型改写，只有亮度被抬升；
* **可解释**：每个像素最终多少 nit 可以用公式算出来，而不是"模型觉得"。

## 2. `hdr.map` 的七步

设 `source` = 原图转场景线性，`source_y` = 其 Rec.709 亮度；`semantic_y` = 模型输出的亮度（1024 长边）。

**① 软阈值（knee / rolloff）**

```
raw = 1 - exp(-max(semantic_y - knee, 0) / rolloff)
```

`knee=2.6` 的含义：场景线性 2.6 以下（≈ 中间调与大部分"白衣服"）**完全不扩展**。
`rolloff` 控制到达饱和的速度。

**② 只对二值掩膜做形态学开运算**

```
eligible = (raw >= support_threshold)   # 0.02
eligible = opening(eligible, support_kernel)   # 15
broad = gaussian(eligible, 3.0)
```

开运算用来去掉**细长响应**（逆光人物轮廓）。
关键细节：**绝不能对连续的 `raw` 做灰度形态学**——那会在平滑高光里造出台阶和条带；
只有二值资格图可以开运算。

**③ 拯救暗背景里的孤立发光点**

```
isolated = (raw >= 0.55) & (blur(source_y_low, 15) <= 0.15)
```

星空、闪光点这类"小而真"的高光，邻域很暗，单独保留。

**④ 用原图边缘锁定位置（导向滤波）**

低分辨率高光先双线性放大到 4K，再以 `source_y` 为 guide 做导向滤波（`radius=10, eps=2e-4`），
最后乘源图亮侧门控 `smoothstep(0.04, 0.32, source_y)`。

结果：**LumiPic 只决定"哪里更亮"，边界位置/锯齿/高频细节全部来自原始 4K 图**，
模型像素无法跨过线稿边界渗出去。

**⑤ 漫反射白门控（flatgate）—— 本项目最关键的一步**

高调赛璐璐图的失败模式：模型把**大面积平坦的白**（头发、装饰）和**亮青色天空**
也判成发光体，于是整块画面"糊成一片亮"。

判据（**与饱和度无关**，因为饱和的青色天空同样是大面积漫反射）：

```
flat = smoothstep(0.55, 0.80, blur(Y, 121)) * (1 - smoothstep(0.03, 0.12, Y - blur(Y, 31)))
```

* 第一项：121px 邻域**平均**就很亮 → 大面积亮区；
* 第二项：像素与 31px 邻域均值差很小 → **平坦**（没有局部结构）。

然后 `flat > 0.5` → 二值开运算(21) → 膨胀(61) → 高斯(σ=18)，得到连续抑制权重 `soft`：

```
gate = 1 - soft * (1 - allow_glow)
highlight *= gate
```

`allow_glow=0` 完全不发光（safe），`=0.1` 保留 10% 弱辉光（balanced）。

**⑥ 绝对亮度映射与色度保持**

```
base_nits   = paper_white_nits * source_y          # 漫反射白 200 nit
target_nits = base_nits + (peak_nits - base_nits) * highlight
chroma      = source / max(source_y, 1e-7)         # 原图色度
nits        = chroma * target_nits
```

色度取自原图，所以肤色、线稿、花纹颜色都不会被改。

**⑦ 渐近肩部（不做硬裁剪）**

```
mapped_peak = paper + (peak - paper) * (1 - exp(-max(channel_peak - paper, 0) / shoulder_width))
nits *= mapped_peak / channel_peak
```

按比例缩放 RGB（保持色相），渐近逼近 `peak_nits`。
`shoulder_width=400` 时 1000 nit 的输入会被压到 ≈892 nit，永远不会"硬切"出平顶。

最后 `scrgb = nits / 80`（Windows scRGB 定义：1.0 = 80 cd/m²）。

## 3. 参数速查

| 参数 | 默认 | 调它的后果 |
|---|---|---|
| `knee` | 2.6 | 调低 → 更多中间调参与扩展（容易整片发亮）；调高 → 只有真正的高光被抬 |
| `rolloff` | 3.2 | 高光过渡的软硬 |
| `paper_white_nits` | 200 | 漫反射白对应的绝对亮度（BT.2408 广播参考是 203） |
| `peak_nits` | 1000 | 目标峰值；肩部会渐近逼近它 |
| `shoulder_width` | 400 | 越小，高光压得越狠 |
| `support_threshold` / `support_kernel` | 0.02 / 15 | 高光资格门槛与去细线强度 |
| `guided_radius` / `guided_eps` | 10 / 2e-4 | 高光贴合原图边缘的紧密程度 |
| `source_gate_low/high` | 0.04 / 0.32 | 限制发光只出现在原图亮侧 |
| `gate` | `flatgate` | `flatgate`（与饱和度无关）/ `whitegate`（亮且低饱和）/ `none` |
| `flat_y_lo` / `flat_y_hi` | 0.55 / 0.80 | **影响最大**：多大的邻域亮度算"大面积亮区" |
| `flat_peak_lo/hi` | 0.03 / 0.12 | 多"平坦"才算漫反射（越小越严格） |
| `flat_open` / `flat_dilate` / `flat_sigma` | 21 / 61 / 18 | 掩膜去噪、覆盖外扩、边缘柔化 |
| `allow_glow` | 0.0 / 0.1 | 保留多少辉光 |
| `strength` | 1.0 | 整体 HDR 扩展强度（0 = 原图） |

## 4. 实测：一次对照复现（2026-10-11）

### 4.1 方法

拿项目里**同一份**输入（`root-photo-4K.png`）与**同一份**语义缓存（`lumipic.npy`），
用本工具重跑参考脚本 `work/root-hdr/map_v2.py` + `gen_flatgate.py` 的算法，
逐项对比参考 README 记录的数字。参考脚本依赖 OpenCV，本工具是纯 numpy 重实现，
所以这同时也是一次**移植正确性**的检验。

### 4.2 结果

| 指标 | 参考记录 | 本次（numpy 移植） | 判断 |
|---|---|---|---|
| 原始档峰值 | 924 nit | **906.8 nit** | ✅ 差 1.9% |
| 原始档 `>500nit` 占比 | 10.84% | **10.12%** | ✅ |
| 原始档受影响面积 | 21.95% | **20.74%** | ✅ |
| 原始档强高光占比 | 9.39% | **9.20%** | ✅ |
| safe 档白色区均值 | 201 nit | **203 nit** | ✅ |
| balanced 档白色区均值 | 249 nit | **270 nit** | ✅ 差 8% |
| safe 档青色区均值 | 202 nit | **202 nit** | ✅✅ |
| balanced 档青色区均值 | 228 nit | **230 nit** | ✅✅ |
| **safe 档全图峰值** | 433 nit | **874 nit** | ❌ 不复现 |
| **balanced 档全图峰值** | 464 nit | **874 nit** | ❌ 不复现 |

结论：**算法链路（①–④、⑥、⑦）与门控的主体效果都复现了**，
但 flatgate 档的**全图峰值**复现不出来。

### 4.3 差异定位

峰值逃逸的像素只有 **4901 个（0.049%）**，集中在三处：左下角的星形闪光装饰、
上方的花环叶片、以及发丝高光。它们的共同特征：

| 量 | 值 | 含义 |
|---|---|---|
| `source_y` | 0.990 | 画面里确实是最亮的一档 |
| `blur(Y, 121)` | **0.617** | 但 121px 邻域均值只有 0.617 |
| `smoothstep(0.55, 0.80, 0.617)` | **0.177** | 第一项就上不去 |
| `flat` 连续值 | **0.16** | < 0.5，**进不了掩膜** |
| `gate` | 1.000 | 于是完全不抑制 |
| 位置 | 距边缘 ≥147px | 不是边界效应 |

也就是说：**门控的判据是"大面积平坦亮区"，而这些装饰性高光点、叶片、发丝按定义就"不平坦"**——
第 ⑤ 步的公式**本来就不会**抑制它们。它们是不是该发光，是一个**产品判断**，
不是实现 bug：星形闪光确实像光源，宽大的平坦白衣才是"错判成光源"的那一类。

### 4.4 想要 460 nit 那种观感怎么办

把亮度 ramp 下移，让"中等大小的亮块"也进入掩膜：

```bash
imgen run pipelines/hdr-retune.json -i source-4K.png \
  --set hdr.semantic.load.path=cache/lumipic.npy \
  --set hdr.map.flat_y_lo=0.45 --set hdr.map.flat_y_hi=0.65 \
  --set hdr.map.allow_glow=0.10
```

实测（同一输入）：

| 配置 | 峰值 | `>500nit` | 抑制面积 |
|---|---|---|---|
| 参考默认（0.55/0.80, allow 0.10） | 874 nit | 0.036% | 63.9% |
| **0.45/0.65, allow 0.10** | **647 nit** | **0.002%** | 81.2% |
| **0.45/0.65, allow 0.00** | **622 nit** | **0.0000%** | 82.0% |
| 0.55/0.80, allow 0.00 | 874 nit | 0.033% | 64.9% |

**建议**：想要"完全不发光"的墙纸观感，用 `0.45/0.65`；
想保留一点辉光，额外把 `allow_glow` 设成 0.1。仓库内
`pipelines/hdr-from-4k.json` 与 `pipelines/anime-4k-hdr.json` 采用前者思路，
`pipelines/hdr-retune.json` 保留参考脚本的原始默认值，方便对照。

> 诚实说明：历史 JXR 文件标注的 433/464 nit **无法**从当前脚本 + 当前缓存严格复现。
> 本仓库不声称复现它，只提供**可解释、可复算**的等效档位。

## 5. 已知边界

* **尺度依赖**：`blur(Y,121)` 在 4K 上约等于画面宽度的 3%。换到 1080p 或 8K，
  想保持同样的"大面积"语义，应按分辨率比例调整 `flat_blur` / `flat_local` / `flat_open` / `flat_dilate`。
* **内存**：4K 帧上 `hdr.map` 峰值会同时持有若干 float32 全图数组（每通道约 40 MB），
  8K 建议分块或先降采样；纯 numpy 的中间量用 float64 累加，精度够但更吃内存。
* **不是母版工具**：这是"把 SDR 观感良好地搬到 HDR 显示"的管线，
  不是 HDR 母版制作（没有真正的场景线性捕获、没有色彩分级环境）。
* **`hdr.semantic.identity` 只是基线**：无模型时高光信号来自源亮度本身，
  不会有"语义"，画面会偏平；日志里会明确提示。
* **JXR 的边界**：Windows 合成器对超出面板峰值的部分是**裁剪**而不是色调映射，
  所以映射必须在编码前做对；也正是因此最终文件的上限被控制在 4K。
