# HDR Still Delivery & Display Engineering on Windows (2026)

Scope: how to author, container-ise, colour-manage and *validate* HDR still images on Windows in 2026.
Method note: every claim below was pulled from primary docs (Microsoft Learn, Android/Google, W3C, libavif/libjxl/libultrahdr repos, ExifTool). Items I could not confirm against a primary source are marked **[unverified]**. Dates are given so you can tell 2024–2026 material from older material.
Tooling note for this research pass: the sandbox's `web_fetch` was unusable (all hostnames resolve into a proxy's `198.18.0.0/15` range and are rejected as non-public), and `web_search` returned only titles/URLs with occasional snippets. Primary pages were therefore retrieved by direct HTTPS through bundled Node.js, which mutates nothing and is reproducible.

## TL;DR

- **Windows' canonical HDR composition space is scRGB, FP16, sRGB/BT.709 primaries, linear gamma — and scRGB `1.0` means 80 nits nominal reference white.** DWM composites in this space; the display kernel converts to BT.2100/ST.2084 on the wire. `scRGB (12.5,12.5,12.5)` = D65 white at 1000 nits. ([1])
- **Windows' built-in HDR wallpaper path is JPEG XR (`.jxr`/`.wdp`) with half-float/fixed-point components.** Shipped as an Insider feature in Aug 2023 (build 25921), GA in Windows 11 24H2 (Oct 2024). Windows picks HDR or SDR rendition per-display. ([2][3])
- **Gain maps are the right answer for *sharing*; true 10/16-bit HDR is the right answer for *mastering*.** Gain maps put the HDR payload inside an 8-bit SDR base image, so naive readers show a correct SDR image; the cost is a downsampled, 8-bit log-encoded payload that cannot express a full HDR master.
- **ISO 21496-1:2025 is the umbrella gain-map metadata standard** (ISO/TC 42/WG 23). Adobe's XMP `hdrgm` namespace (v1.0) is the JPEG/Ultra-HDR carriage; Apple brands the ISO format **Adaptive HDR**; Google's **Ultra HDR** is an Adobe-licensed gain-map scheme shipped in Android 14 (Oct 2023), spec **v1.1** (2024-10-25). ([4][5][6])
- **Since Android 15 (API 35), Ultra HDR JPEGs carry *both* `hdrgm` (v1) and ISO 21496-1 metadata; decoders should prefer ISO 21496-1 when both are present.** That is a 2024/2025 change worth exploiting for cross-platform files. ([6])
- **As of 2026 the biggest change is libultrahdr v2.0.0 (2026-08-07): gain maps in HEIF/HEIC *and* AVIF, not just JPEG**, with ISO 21496-1 metadata carried as an ISOBMFF **`tmap` derived tone-map item** referenced via `dimg`, plus an `uhdr_dec_probe()` that auto-detects JPEG/HEIF/AVIF by magic bytes. v2.0.2 landed 2026-08-13. ([7][22])
- **ICC did not just propose a gain-map tag — it shipped one.** `ADGC` / `adaptiveGainCurveType` was **added to the ICC.1 specification on 2025-04-17**: a gain-based global tone-mapping curve for SDR↔HDR conversion, normative against ISO 21496-1, carrying log2 baseline/alternate headroom and a piecewise-cubic gain curve. Apple exposes authoring APIs through ColorSync. **This is the first format-agnostic home for a gain map**, but no Windows consumer exists yet. ([21][28][29])
- **libavif's gain-map API went non-experimental in libavif 1.2.0 (2025-02-25)**, which also shipped the `avifgainmaputil` CLI. Current line: 1.4.2 (2026-05-26), with 1.4.0 (2026-03-04) adding **Apple-style gain map JPEG → AVIF conversion and PNG `cICP` decode**. ([8])
- **JPEG XL HDR finally has mainstream browser support in 2026**: Chromium merged JXL decoding Jan 2026, Google shipped it GA in **Chrome 155 (Oct 2026)**; Firefox shipped JXL in 152 (Jun 2026) behind a flag, default-on slated for 158 (Oct 2026). Safari 17+ has had it since 2023. ([9])
- **PNG is now a legitimate HDR still container**: PNG Third Edition adds `cICP`, `mDCV` (ST.2086 mastering display), `cLLI` (MaxCLL/MaxFALL) and **`hRWL` (HDR Reference White Level)**. `cICP` is the highest-precedence colour chunk and *supersedes* `iCCP`. ISO 22028-5 — the HDR/WCG still-image encoding standard the PNG work follows — reached **IS status in 2026** (it was a TS in 2019). ([10][21][23])
- **WIC's HDR output is a minefield**: it hands you HDR pixels as un-tagged FP16 scRGB with no diffuse-white signal, and the JXL/AVIF WIC codecs have documented bugs (P3 decoded as BT.2020 → oversaturated; no native downscale → slow thumbnails). ([11][12])
- **Practical Python takeaway:** on a stock Windows box you get little for free — Pillow 12.3 reads/writes AVIF and 16-bit modes but has **no gain-map, JXR, JXL or HEIC support**; no ffprobe/exiftool/libavif CLIs are installed here. Budget for bundling `libavif`/`libultrahdr`/`jxrlib` binaries or driving `WIC` over COM. ([13])

### Decision guide

| Goal | Use | Why |
|---|---|---|
| Share one file that looks right on every screen | Ultra HDR JPEG, ISO 21496-1 metadata written *alongside* `hdrgm` | Backward-compatible 8-bit base; widest 2026 client coverage ([6]) |
| Master an HDR still for further editing | 16/32-bit float (EXR, JXR half-float, JXL float) + PQ or linear | Gain maps are a delivery format, not a master ([3][6]) |
| Native HDR in a modern browser | AVIF 10-bit PQ/HLG, or JPEG XL | AVIF >93% browser reach; JXL GA in Chrome 155 (Oct 2026) ([9][18]) |
| Windows desktop HDR wallpaper | JPEG XR, half-float/fixed-point, scRGB-linear | The only path the shell renders as HDR ([2][3]) |
| Lossless HDR archival with metadata | PNG 16-bit + `cICP`/`mDCV`/`cLLI`/`hRWL` | Explicit absolute-luminance intent in the container ([10]) |
| Apple-ecosystem HDR sharing | HEIC with Adaptive HDR (ISO 21496-1) gain map | What iOS/macOS expect ([16]) |

### What Windows' built-in HDR wallpaper actually expects

- Format: a **`.jxr`** file (JPEG XR). Set via Settings → Personalisation → Background, or right-click desktop.
- Colour encoding: **scRGB-style linear-light with sRGB/BT.709 primaries**, stored as half-float or fixed-point components — i.e. the same CCCS DWM composites in, so no gamut conversion is needed. `1.0` should be treated as **80 nits** nominal reference white, exactly as D2D's `D2D1_SCENE_REFERRED_SDR_WHITE_LEVEL`. ([1])
- Per-display behaviour: with multiple displays, Windows renders the wallpaper as HDR or SDR **per display capability**; external displays benefit from running the Windows HDR Calibration app first. ([2])
- Microsoft explicitly acknowledged early defects with the HDR background on *some* laptops in the announcing build. ([2])
- **Known limitations I could not source**: no official Microsoft doc states a maximum JXR resolution or file-size cap, nor a documented requirement that the JXR be 16-bit half-float specifically. **[unverified]** Treat "huge JXR wallpapers may fail or decode slowly" as folklore until tested.
- Because WIC's JXR encoder is `CLSID_WICWmpEncoder` and WIC supports **up to Main Profile / level 128**, very large single-image JXR files are the real constraint in practice (tiles must be ≥16×16 px; `HorizontalTileSlices`/`VerticalTileSlices`). ([3][14])

## Format details: what it is, support, pros/cons

**Gain maps (Ultra HDR / ISO 21496-1 / AVIF gain map / Adaptive HDR).** A map of per-pixel *ratios* between an SDR base image and an HDR alternate, log2-encoded and quantised to 8 bits. The decoder computes `log_boost = gain_map_min*(1-log_recovery) + gain_map_max*log_recovery`, then `HDR = (SDR + offset_sdr) * exp2(log_boost * weight_factor) - offset_hdr`, where `weight_factor` is derived from the *current display boost* vs `HDRCapacityMin/Max`. That display-adaptive weighting is the whole point: the same file renders correctly whether the display can do 1.2× or 4× SDR white. ([6])
- *Support 2026:* Adobe (`hdrgm` XMP), Google/Android 14+ (Ultra HDR; Android 15+ writes ISO 21496-1 too), Apple (Adaptive HDR, iOS 18+), Chrome/Edge/Opera/Brave, Safari, libavif ≥1.2.0, libultrahdr 2.0.x (JPEG **and** HEIF **and** AVIF). AOMedia's April 2025 release note for libavif 1.2.0 names Chrome, Edge, Android and Apple's operating systems as gain-map capable and says nothing about Firefox. ([18][26])
- *Pros:* one file, no HDR/SDR variants to manage; degrades to a real SDR image; tiny overhead (map often ¼×¼); display-adaptive by construction; partially future-proof because ISO 21496-1 is container-agnostic.
- *Cons:* bounded HDR volume — 8-bit log map, usually downsampled, map colour profile ignored; cannot express true 10/12-bit PQ headroom or precise highlight gradations; needs encoder support you must bundle; the *reader* must implement the exponential formula correctly or tonal relationships break at non-maximal display boost. **A gain map is not a substitute for a 10/16-bit HDR master; it is a substitute for shipping two files.** ([6])

**JPEG XR / JXR (scRGB half-float).** ITU-T T.832 / ISO/IEC 29199-2, derived from HD Photo; supports 8/16/32-bit integer, 16/32-bit fixed-point and **16/32-bit floating point** as well as RGBE. In fixed point, the top bits are headroom/toe-room beyond nominal black→white: 16-bit is s2.13 with `1.0 = 0x2000`, total range −4.0…+3.999; 32-bit is s7.24 with `1.0 = 0x01000000`, range −128…+127.999. ([3][14][20])
- *Pros:* the only format Windows' shell renders as an HDR wallpaper; WIC encoder is in-box since Windows 8; float support is genuinely HDR-capable; tile-based (min 16×16 px) so regions decode independently.
- *Cons:* near-zero web/portable support; no HDR10-style static metadata model; the practical encode path on Windows is WIC COM (no clean Python binding); large wallpapers hit Main Profile / level 128 and tile-overhead limits; Photoshop's HDR JXR export is the pragmatic authoring route **[unverified]**.

**AVIF (10/12-bit PQ/HLG).** AV1-in-ISOBMFF. WIC decodes it (24H2+ for HDR), the AVIF Image Extension has been built into Windows 11 since 22H2, and all major browsers have supported it since 2024. Carries CICP via `colr`/`nclx` (which by MIAF overrides bitstream CICP), `clli` and `mdcv`. ([8][14][18])
- *Pros:* best combination of browser reach, colour precision, and HDR signalling; gain maps now first-class (libavif 1.2.0+, Feb 2025); `avifgainmaputil` gives you compute/apply/tonemap on the CLI; the CICP refactor means ICC and CICP coexist instead of excluding each other.
- *Cons:* encode cost and complexity; WIC's HDR AVIF decode path has the white-level problem (pitfall 2); gain-map support in Firefox is absent **[unverified]**; still no *shipping encoder* in some non-libavif stacks (Wikipedia's AVIF article as of mid-2026 still claims none) — always verify your chosen encoder actually writes ISO 21496-1, not just the base image.

**JPEG XL (HDR).** ISO/IEC 18181; sample precision up to 32 bits, float16 round-tripping, PQ/HLG/Rec.2100 built in, and a dedicated `jhgm` gain-map box whose metadata is *literally an ISO 21496-1 binary blob* with an optional alternative ICC profile (`JxlGainMapBundle`, `JxlGainMapReadBundle`/`WriteBundle`). libjxl 0.12.0 shipped 2026-07-01. ([9][19])
- *Pros:* the cleanest HDR still container technically; one format for SDR, HDR, lossless and lossy; native gain-map box rather than a bolted-on secondary image; `djxl --tone_map --display_nits` makes honest SDR previews easy; revived 2025 PDF Association interest as the preferred embedded HDR image format.
- *Cons:* a decade of false starts — Chrome support was added Apr 2021, **removed in Chrome 110 (Dec 2022)**, and only restored to GA in **Chrome 155 (Oct 2026)**; Firefox default-on slipped to 158; the Windows WIC codec is an optional Store add-on with four documented defects (pitfall 2–5). Do not build a 2026 pipeline that assumes JXL everywhere.

**HEIC/HEIF 10-bit + Apple Adaptive HDR.** ISOBMFF with HEVC; Apple's Adaptive HDR is the ISO 21496-1 gain map in a HEIC container. ExifTool exposes Apple's `XMP-HDRGainMap` family separately from Adobe's `XMP-hdrgm`. ([16][17])
- *Container mechanics (2026, worth knowing before you implement):* HEIF/AVIF Ultra HDR per ISO/IEC 23008-12 + ISO 21496-1 stores the metadata as an **uncompressed `tmap` (derived tone map) item**, which references the base image (index 0) and gain-map image (index 1) through a **`dimg`** derived-image reference box; **NCLX (`colr`) and ICC boxes attach to the derived item** as well as to the gain-map item. libultrahdr v2.0.x implements this through `libheif` and adds the gain map as an **auxiliary track**; pre-compressed-input transcoding is *not* supported for HEIF/AVIF (returns `UHDR_CODEC_UNSUPPORTED_FEATURE`). ([22])
- *Pros:* native to Apple platforms; 10-bit HEVC base is high quality; ISO 21496-1 makes it interoperable in principle.
- *Cons:* **libheif upstream needed a patch to support ISO 21496-1 gain-map APIs** — libultrahdr v2.0.1 (2026-08-10) bundles and auto-applies it, and falls back with a warning if the system libheif lacks it. If you build your own HEIF stack, verify this explicitly. Windows has no HEIC wallpaper path.

**PNG (HDR PQ).** PNG Third Edition (2025) adds `cICP` (4 bytes: primaries, transfer, matrix, full-range flag), `mDCV` (ST.2086 mastering display — must be accompanied by `cICP`), `cLLI` (MaxCLL/MaxFALL), and **`hRWL`** (HDR Reference White Level, default 203 cd/m², i.e. 58% PQ / 75% HLG on a 1000 cd/m² display; non-default values signal non-standard white). `cICP` is the highest-precedence colour chunk, so it **overrides `iCCP`/`sRGB`** when present. Canonical `cICP` values: BT.2100 PQ full-range `09 10 00 01`; BT.2100 HLG `09 12 00 01`; BT.709 narrow `01 01 00 00`; Display-P3 full `0C 0D 00 01`. ([10])
- *Pros:* lossless, universally parseable container, now with first-class absolute-luminance signalling; `hRWL` directly solves the "what is diffuse white" ambiguity that WIC leaves open.
- *Cons:* 16-bit integer only — no float, so real scene-referred HDR needs care; browser/renderer HDR support for PNG is still uneven; note libavif 1.4.0's rule that a PNG `cICP` chunk causes other colour chunks to be **ignored** (PNG Third Ed §4.3), so a mixed-metadata PNG will surprise you. ([8][10])

**EXR.** 16-bit half / 32-bit float, linear, scene-referred, arbitrary attributes. No OS display path, no browser path. Use it as an intermediate/master format inside the pipeline and convert on export.

## Colour management

- **scRGB vs PQ vs HLG vs linear.** scRGB is *scene/display-referred linear light* with unbounded numeric range, primaries fixed to sRGB/BT.709. PQ (ST.2084) is an absolute display-referred OETF over 0–10 000 cd/m² with BT.2020 primaries in HDR10. HLG is a *relative* system. Windows chose scRGB/FP16 for composition because PQ is bad at blending and cannot represent the full colour volume; PQ is only the **wire format**. ([1])
- **sRGB → scRGB is a pure linearisation, no matrix.** Same primaries, so decode the sRGB EOTF and you are done. Then to reach a target luminance: multiply by `nits / 80`. Windows' own guidance is literally `SDR_color_value * (SdrWhiteLevelInNits / 80)`. If you are in a non-linear space (HDR10/PQ), you must go via linear gamma to do this correctly. ([1])
- **80 nits is the *nominal* reference white; the *configured* SDR white level is what you must actually match.** On desktop HDR monitors `AdvancedColorInfo.SdrWhiteLevelInNits` is typically around **200 nits**. Apps that compose SDR and HDR into one surface themselves (rather than letting the OS compose) are responsible for this boost; get it wrong and SDR content looks dim. ([1])
- **ICtCp / ΔE-ITP.** BT.2100 defines ICtCp (CICP matrix coefficients 14) as a perceptual, constant-luminance HDR signal format. The matching *colour-difference* metric is standardised, not folklore: **ITU-R BT.2124-0** defines ΔE-ITP as `720 · √((ΔI)² + (ΔT)² + (ΔP)²)` in scaled ICtCp (I, T = 0.5·Ct, P = Cp), where **ΔE-ITP ≈ 1.0 is one just-noticeable colour difference** under the most critical adaptation state and identical frames score exactly `0.0`. The normative pipeline is BT.2124-0 Annex 1 with a worked example in Annex 4. Two implementation traps worth copying from a working implementation: **out-of-gamut negative LMS/ICtCp values must not be clamped** (or you stop measuring exactly the clipping errors you care about), and the metric is **PQ-only** — feeding HLG or SDR content through a PQ-based ΔE-ITP implementation produces meaningless numbers. Use ΔE-ITP instead of ΔE2000 for any PQ/WCG still comparison; ΔE2000 is an SDR/BT.709 metric. ([27])
- **DisplayP3 vs BT.2020 for still HDR.** Gain-map specs are explicit: **the SDR base image's ICC profile defines the HDR rendition's primaries.** Google's Ultra HDR spec *tips Display-P3* for the primary image, and therefore the HDR rendition is Display-P3 too. For true 10/12-bit HDR10-style stills the convention is BT.2020 + PQ. Practical rule: gain map → Display-P3 primaries + linear/gain ratio; native HDR still → BT.2020 + PQ (+`mDCV`/`cLLI`). ([6][10])
- **How ICC interacts with an HDR display on Windows.** Two distinct regimes: ([1])
  - **SDR / Advanced Colour (ACM):** the display kernel converts the OS framebuffer into the display's own colorimetry from its calibration data; ICC profiles matter and ACM shapes SDR output.
  - **HDR on:** composition is a fixed scRGB/BT.709-primaries space, and conversion to BT.2100/ST.2084 happens downstream. An embedded ICC profile cannot describe an absolute-luminance HDR rendition on its own, which is exactly why gain-map and ISO 21496-1 files pair the ICC profile with *numeric* metadata rather than trusting the profile alone ([6]).
- **ICC's own position (2024→2026), which settles the "ICC vs CICP" question for stills.** At the ICC/ISO joint HDR expert day: ICC is **not defining a gain map**, it is "trying to embrace existing methods." A **gain-map tag (with luma scaling) was proposed for technical review, initially in ICC.1 then ICC.2** — and it duly shipped (next bullet). The proposed transform order is **source profile → gain map → destination profile**, with the gain map as an intermediate stage in an otherwise normal ICC transform chain; because the gain map is linear, it is compatible with the ICC PCS. **CICP is required for HDR images in ICC and optional for SDR**, and the post-gain-map CICP tag identifies the final output space. Precedence is explicitly acknowledged to be format-dependent — e.g. **PNG gives `cICP` precedence over the ICC profile transform** — and ICC's stated aim is consistent interpretation even when ICC is secondary. Practical consequence: put primaries/transfer in CICP *and* keep a correct ICC profile, and never assume a CMM will apply a gain map for you. ([21])
- **ICC actually shipped the gain-map tag: `ADGC` / `adaptiveGainCurveType`, added to the ICC.1 specification on 2025-04-17** — the concrete outcome of the 2024 proposal above. It defines "a gain-based global tone mapping curve for an SDR or HDR image", may be present only when the data colour space is RGB and the profile class is Input or Display, and is normative against ISO 21496-1. The tag carries a 4-byte type signature `adgc` (`61646763h`), a function-type ID (= 1 in this version), **a 16-byte GUID that is all zeros unless the curve is image-specific** (in which case the profile header's embedded/not-usable-independently flags must be set), `baseline headroom` and `alternate headroom` in **log base 2** (the same headroom concept as ISO 21496-1's `baseHdrHeadroom`/`alternateHdrHeadroom`), then per-RGB **up-to-cubic curve coefficients and weight coefficients**, including `MAX(R,G,B)` and `MIN(R,G,B)` weights. The curve function is normative and three-stage: an input evaluator (a weighted sum over R, G, B, MAX(RGB), MIN(RGB) and the channel itself), a **gain evaluator as a piecewise cubic** `F(x) = C3x³ + C2x² + C1x + C0` anchored by `{x1,y1,slope1}…{x2,y2,slope2}` triplets, and an output evaluator. Apple exposes exactly this through ColorSync (`ColorSyncProfile.adding(headroomAdaptiveGainCurve:)` and `adding(headroomAdaptiveGainCurveMetadata:options:)`, with a `HeadroomAdaptiveGainCurveOptions` type), and documents an "Authoring Headroom-Adaptive Gain Curve Metadata" guide. **Implication for a Windows pipeline: the gain map can now live in the ICC profile itself, which is the first genuinely portable, format-agnostic home for it.** ([28][29])
- **Windows HDR Calibration app.** Sets per-display **minimum luminance**, **maximum luminance** and **full-frame luminance** (the three-panel test), which feed `DXGI_OUTPUT_DESC1` and hence what tone mappers see. One Microsoft Q&A answer describes the sliders as a 0–1 relative minimum and a 200–2000 nit maximum — that answer is a community/support reply, so treat the exact ranges as **[unverified]**, but MS's own build notes do confirm calibration is what makes external-display HDR backgrounds look right. ([2][15])
- **ACM / "Automatically manage colour for apps"** requires **Windows 11 22H2+** and is an SDR-wide-gamut feature; `IDXGIOutput6` explicitly **cannot distinguish an SDR ACM display from a plain SDR display** (both report `DXGI_COLOR_SPACE_RGB_FULL_G22_NONE_P709`) and cannot report supported-but-inactive Advanced Colour kinds. Plan for opacity. ([1])
- **Tone mapping by the compositor: there isn't any.** DWM composites; where content exceeds the display, **"DWM will downconvert your content to fit the display's capabilities by performing numeric clipping."** If you render FP16 scRGB at a target that only does SDR, everything outside `[0,1]` is clipped. The same clipping applies to a window straddling displays of differing capability, and capability queries only describe the display under the window's centre. ([1]) **Consequence for stills: your writer must tone map; Windows will not do it for you.**

## Validation tooling

- **WIC (the one path that is always present).** Decode `.jxr`/AVIF/HEIC through `IWICImagingFactory` and inspect `IWICBitmapSource::GetPixelFormat` — HDR shows up as `GUID_WICPixelFormat64bppRGBAHalf` (16-bit float), `GUID_WICPixelFormat32bppR10G10B10A2HDR10` (10-bit BT.2020 + ST.2084), `48bppRGBHalf`, or the 128bpp float formats. Read the colour context via `IWICColorContext`; get `GUID_WICPixelFormat64bppRGBAHalf` + no colour context and you are in the un-tagged scRGB case. **WIC's inference rule: UINT RGB/grey → sRGB; fixed-point and floating-point RGB/grey → scRGB.** ([14]) From Python this means `pywin32`/`comtypes` against the WIC COM API (no first-class binding), or a small bundled helper binary.
- **`avifdec` / `avifdump` / `avifgainmaputil` (libavif ≥1.2.0).** Since the CICP refactor, `avifenc`/`avifdec`/`avifdump` all print CICP on dump, and the `nclx`/`colr` box is guaranteed to override AV1-bitstream CICP (per MIAF). Use `avifgainmaputil` to compute, apply and re-quantise gain maps, and note the `--ignore-icc` flag if you need pixels untouched by profile handling. ([8])
- **`ffprobe`.** Reads container-level colour tags (`color_primaries`, `transfer_characteristics`, `matrix_coefficients`), plus `clli`/`mdcv` on supported paths. It is *not* installed in this environment, so a pipeline must ship it. ([13])
- **`exiftool`.** The definitive cross-check for gain-map metadata: families `XMP-hdrgm` (Adobe) and `XMP-HDRGainMap` (Apple), plus PNG chunk tags — notably **`cICP` → `CICodePoints`** (with a nested `PNG CICodePoints` family) and **`gdAT` → `GainMapImage`**. ExifTool also reads gain-map blobs in MPF trailers and as `hdgm`/`hrgm`/`GAINMAP0`/`GAINMAP1`. Note ExifTool's PNG chunk table as retrieved does not list `mDCV`/`cLLI`/`hRWL`, so do not treat "exiftool showed nothing" as "no HDR metadata". Not installed here. ([17][24])
- **`jxrlib` / `djxl`** for JXR and JXL respectively. `djxl` supports optional HDR tone mapping (`--tone_map`, `--display_nits`), which is the honest way to preview what an SDR host will show. ([9])
- **Display-side verification (the other half of "validation").** File inspection proves intent; only measurement proves output. `mpv` reads AVIF and is useful as a known-good HDR *renderer* for A/B against the Windows shell; **madVR** and **ColourSpace/Calman** (+ a colorimeter) are for measuring actual on-screen luminance against the values you configured in Windows HDR Calibration (min / peak / full-frame). `DXGI_OUTPUT_DESC1` is the programmatic middle ground: it exposes the panel's physical colour volume as ST.2086-equivalent luminance/chrominance numbers for both HDR *and* SDR displays. ([1][25])
- **One more display-side caveat that bites certification claims:** VESA **DisplayHDR 1.2** (published late 2024, effective 2025-05, mandatory from 2026-05) tightened the tiers — DCI-P3 coverage requirements appear at lower tiers, higher tiers move to 1400, and FRC/bit-depth requirements stiffened (roughly 8+2 under v1.1 → 10-bit under v1.2). A "DisplayHDR 400" badge therefore means something different depending on when the panel was certified, which matters when you use a display's rated peak to decide gain-map headroom. ([25])
- **What to check, minimally, for any HDR still:** container + codec; primaries/transfer/matrix (CICP); presence and *values* of `mDCV`/`cLLI`/`hRWL`; presence of ICC and whether its primaries agree with CICP; gain-map metadata (`hdrgm` version + GainMapMin/Max/Gamma/Offsets/HDRCapacityMin/Max, the ISO 21496-1 equivalents, or an ISOBMFF `tmap` item); and whether diffuse white is recoverable.

## Pitfall catalogue

1. **Missing peak-luminance metadata → the reader guesses.** Without `mDCV`/`cLLI` (or ISO 21496-1 headroom), a tone mapper can only assume worst-case content. Windows' documented adapt-to-display guidance names max luminance ("MaxCLL") as the single most important parameter. If you omit it, you get a mismatch between authored intent and rendered output. ([1][10])
2. **White-level ambiguity in WIC's HDR decodes — the flagship Windows pitfall.** WIC returns HDR AVIF/HEIC/JXL as FP16 **with no colour space and no diffuse-white signal**; the submitter's argument is that `(1,1,1)` should mean diffuse white (JPEG XR T.832 p.181: "the scRGB perfect diffuse white point is specified by all three colour channels set to a value of 1.0"). Real consequence: when you transcode or thumbnail via WIC, the reference white of your output drifts. ([11])
3. **Wrong primaries in the WIC JXL path.** A Display-P3 HDR JXL was decoded as if BT.2020 → visibly **oversaturated**. Any HDR pipeline that trusts WIC's colour conversion needs an independent CICP/ICC cross-check. ([12])
4. **16-bit SDR decoded to float.** The WIC JXL codec decodes 16-bit integer SDR images to 16-bit float, reducing precision, increasing decode time, and amplifying pitfall 2. ([12])
5. **No native downscale in the WIC JXL codec** → thumbnail generation of large JXL files is slow (worse than JPEG). Anything that builds Explorer-style thumbnails, or a wallpaper picker preview grid, inherits this. ([12])
6. **Double tone mapping.** The compositor clips rather than tone maps ([1]), but *players and apps* tone map. Combine an already-tone-mapped file (or a gain map applied at a second headroom) with an app-level tone mapper and you get flat, desaturated highlights. Test at the display's calibrated max, not at a nominal 1000 nits.
7. **Clipping at `[0,1]` on SDR downconversion.** Rendering scRGB values above 1.0 to a non-HDR or straddled-window target clips them outright. Author a deliberate SDR rendition — that is precisely the problem gain maps exist to solve. ([1][6])
8. **Banding in near-flat HDR gradients.** An 8-bit gain map stretched over a 4–5 stop boost has ~256 levels of *ratio*, so smooth sky gradients acquire contouring that was invisible in the SDR base. Mitigations: 10-bit+ base where the container allows (AVIF/HEIC), lossless/near-lossless gain-map coding, `map_gamma` > 1.0 when detail piles up just above SDR range, and **ordered/blue-noise dither at the final quantisation step**. The spec's own advice: `offset_sdr`/`offset_hdr` = 1/64 balances near-black recovery against map precision — raising them too far *reduces* precision. ([6])
9. **Gain-map precision limits are structural, not a bug.** The map is capped at 8-bit unsigned, `[0,255]`, `encoded_recovery = floor(recovery*255 + 0.5)`, typically downsampled to 1/16 the pixel count (¼ each axis), and its colour profile is ignored. Also: `Ysdr` and `offset_sdr` both zero is *implementation-defined*. Do not treat a gain-map file as a substitute for a 10/12-bit HDR master. ([6])
10. **Applying the gain map linearly instead of exponentially breaks tonal relationships.** The spec is explicit: `HDR = (SDR + offset_sdr) * exp2(log_boost * weight_factor) - offset_hdr`. Any "just lerp it" implementation is only correct at max content boost and wrong at every other display boost. ([6])
11. **Overshoot / halos around high-contrast edges.** Range compression (local tone mapping) is how HDR scenes become SDR bases; edge-aware operators trade local contrast for halos if pushed. Combined with sharpening before gain-map derivation, bright edges overshoot. Author the SDR base with the gain map in mind, and derive the map *after* any sharpening.
12. **Wallpaper at 100 % vs thumbnail.** The Windows shell, pickers and any non-HDR preview path will render the SDR base (or a WIC-converted rendition). A wallpaper whose HDR intent is carried by a big highlight boost looks *flat* at 100 % but can look *wrong* in thumbnails if the base was authored as a dimmed HDR tone map. Rule: make the SDR base a first-class deliverable, not a by-product. ([2][6])
13. **Multi-display capability is opaque and mid-window.** Advanced Colour capability can change while your app runs (poll `IDXGIFactory1::IsCurrent`), capability queries describe only the display under the window centre, and DXGI cannot distinguish SDR-ACM from plain SDR. Do not design a wallpaper pipeline that assumes one display class. ([1])
14. **Dolby Vision / HDR10+ for stills is a dead end on Windows desktop.** HDR10 (PQ + ST.2086 + MaxCLL/MaxFALL) is the baseline Windows requires; "a high dynamic range display must implement the HDR10, or BT.2100 ST.2084, standard." Dynamic-metadata stills have no wallpaper or shell path — spend the effort on HDR10-style static metadata plus a gain map instead. ([1][10])

## Practical Python / Windows offline pipeline

What is actually available on this machine (probed, not assumed): Python 3.12.14 with **Pillow 12.3.0** (`features.check("avif") == True`, `jpg_2000`, `webp`, `libtiff`, `zlib`) and numpy 2.3.5. **Not** installed: `cv2`, `imageio`, `tifffile`, `imagecodecs`, `OpenEXR`, `pyvips`, `av`, `wand`, `skimage`, `colour`, `rawpy`, `pyheif`, `pillow_heif`. Pillow registers `.avif` but **not** `.jxr`, `.heic` or `.jxl`. No `ffprobe`, `ffmpeg`, `magick`, `vips`, `exiftool`, `avifenc/dec`, `cjxl/djxl` or `uhdr_enc` on PATH. ([13])

Read that as the baseline cost of the project:

| Need | Realistic route | Caveat |
|---|---|---|
| Read/write 8-bit SDR base images | Pillow + numpy | Fine |
| Read/write AVIF 10-bit | Pillow + libavif (may need `avifenc`/`avifdec` for CICP control) | Pillow exposes ICC/EXIF/XMP but **not** CICP, `clli`, `mdcv` or gain maps |
| Gain maps (create/apply/transcode) | Bundle `libavif` `avifenc`/`avifdec`/`avifgainmaputil` ≥1.4.x, or `libultrahdr` 2.0.x, via `subprocess` | Native binaries; validate their presence at startup and fail loudly |
| Write JXR for HDR wallpaper | WIC COM (`CLSID_WICWmpEncoder`) via `pywin32`/`comtypes`, or bundle `jxrlib` | Needs `GUID_WICPixelFormat64bppRGBAHalf` (or 16/32-bit fixed-point) and a linear scRGB write; **tone map yourself** — DWM clips |
| Verify what a file contains | Bundle `exiftool` (best metadata coverage) + `ffprobe` | Do both: exiftool sees XMP/`hdrgm`/PNG chunks, ffprobe sees container CICP/`clli` |
| Measure on-screen result | External: ColourSpace/Calman + a colorimeter; madVR/mpv as reference renderer | Not automatable in-process |
| Handle ICC ↔ CICP precedence | Decide precedence explicitly and record it | libavif: PNG `cICP` makes other colour chunks ignored; WIC: float/fixed-point ⇒ scRGB inference |

Three verification habits worth encoding as tests, given pitfalls 2–5:
1. **Assert diffuse white** round-trips: write a 5%-grey patch and a `(1,1,1)` patch, decode through *both* your library path and WIC, and assert the ratio matches the intended reference white.
2. **Assert primaries** survive: author a known Display-P3 saturated patch and check for the WIC P3→BT.2020 oversaturation signature ([12]).
3. **Golden-image the SDR fallback**: decode the gain-map file with gain maps *disabled* and diff against your intended SDR rendition. This is the image most viewers will actually see.

## Uncertainty register

- **Environment limitation, not a research gap:** `web_fetch` is non-functional in this sandbox (every hostname resolves into a proxy's `198.18.0.0/15` range and is rejected as non-public), and `web_search` returned only titles/URLs with occasional snippets — no summary bodies. All primary content was therefore retrieved by direct HTTPS through bundled Node.js. Nothing in this report is based on a page I did not successfully retrieve, except where explicitly marked.
- **JXR wallpaper limits [unverified]:** no Microsoft source found stating a max resolution, max file size, required bit depth, or the exact expected pixel format/colour space for `.jxr` wallpapers. The scRGB/80-nit expectation is inferred from DWM's documented CCCS, not from a wallpaper-specific doc. **Test this before relying on it.**
- **HDR Calibration slider ranges [unverified]:** the only source found is a Microsoft Q&A *community/support* answer describing min luminance as a 0–1 relative scale and max as 200–2000 nits. The three quantities (min / peak / full-frame) are well established, but the numeric ranges are not confirmed by a first-party doc. The official support article could not be retrieved (403/404).
- **Firefox gain-map (Ultra HDR) support:** I found no primary confirmation of gain-map rendering in Firefox in 2026; Android/AOMedia statements list Chrome, Edge, Android and Apple. Treat "Firefox does not render gain maps" as probable-but-unconfirmed.
- **ISO/IEC 26892:** a standards-document reference quoted wording associating HEIF-based HDR (ISO/TS 22028-5) with gain-map-based "Adaptive HDR" in an ISO/IEC 26892 context. The PDF at that URL was not machine-readable (20 bytes returned), ISO's site blocked the request, and I could not confirm the part number, title or stage. **Do not cite ISO 26892 on this report's authority.** What *is* confirmed: **ISO 22028-5 reached IS status in 2026** (standard 87778), and the ICC deck's own timeline slide reads `ISO HDR TS 22028-5 (2019) → ISO Gain Map NP 21496-1 (2023) → ISO HDR IS 22028-5 (2026)` with `IS 21496-1 (2025)`, independently corroborating the 21496-1:2025 and 22028-5:2026 dates. ([21][23])
- **ICC `ADGC` adoption is confirmed from the ICC's own spec** ("added to the ICC.1 specification on 17 April 2025"), so that date is solid. Two caveats: the spec references a draft (`ISO 21496-1:20XX`) rather than the published edition, and **I found no Windows or third-party consumer of `ADGC`** — Apple's ColorSync authoring APIs are the only implementation I could confirm. Treat `ADGC` as available-to-write but not yet widely readable.
- **`ADGC` encoding detail I could not fully parse:** the PDF text-extraction of the header table mangled the byte offsets and the actual symbol names for the curve coefficients (they render as empty where the spec uses mathematical notation). The *structure* below is reliable; re-read the PDF directly if you implement a writer.
- **JPEG XL browser dates:** exact GA build numbers (Chrome 155, Firefox 158) come from the Wikipedia JXL article's October 2026 citations. The direction is well corroborated (Chromium merged JXL Jan 2026; libjxl 0.12.0 shipped 2026-07-01; Firefox 152 Jun 2026), but re-check Chrome/Firefox release notes before quoting a version.
- **AVIF gain-map encoder availability:** Wikipedia's AVIF article still asserted "no encoder is currently available" for AVIF gain maps, which **contradicts** libavif's own changelog (gain map API live since 1.2.0, Feb 2025), AOMedia's April 2025 announcement, and libultrahdr v2.0.0 (AVIF gain-map encode/decode, Aug 2026). I trust the repo changelogs and AOMedia; the Wikipedia claim is stale. Noted because it shows how far secondary sources lag here.
- **AVIF 1.2 / AV2:** AOMedia's 2026-02-01 year-in-review confirms an **AVIF 1.2** release and the **AV2 draft specification** for public review. It does not say whether either changes still-image gain-map handling, and I did not retrieve the AVIF 1.2 spec. Check new box types before relying on them.
- **Retrieval failures worth knowing:** `w3.org` (403), `support.microsoft.com` (403/404), `iso.org` (403), `lists.w3.org` (Cloudflare 403), `color.org` (connect timeout), `helpx.adobe.com` (connect timeout), `gregbenzphotography.com` (403), GitHub REST API (403 rate limit mid-session). **Adobe's own Gain Map v1.0 spec PDF was therefore never directly retrieved**; the Ultra HDR v1.1 spec and ExifTool's tag tables were used as substitutes.
- **Not researched / out of scope:** ICC MAX beyond the gain-map-tag proposal, AV2-based still images, JPEG AI, Apple's gain-curve patents, Samsung/Intel Windows-HDR power work, and HDR in PDF (the PDF Association's Sept 2025 preference for JXL as the embedded HDR image format is noted but unexplored).
